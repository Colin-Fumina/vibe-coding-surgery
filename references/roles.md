# 红蓝双角色（可选，重大改动时用）

自己审自己有天然的自我合理化。重大改动分两个会话。

---

## 分工

| 角色 | 给什么 | 不给什么 | 只干一件事 |
|---|---|---|---|
| **蓝队（执行）** | TASK.md + 本 skill + 目标文件 | —— | 按计划改一片，跑验证，报结果 |
| **红队（审查）** | 本 skill + 症状清单 + **diff** | **蓝队的对话历史、它的解释、它的"为什么这样改"** | 只拿 diff 和仓库，跑命令，找偷工减料 |

---

## 红队具体查什么

四条，全是对 diff 的机械检查：

```bash
# 1 有没有删掉/注释掉测试断言
git diff HEAD~1 | grep -E "^-\s*(expect|assert)"

# 2 有没有偷偷放宽类型
git diff HEAD~1 | grep -E "^\+.*(\bany\b|@ts-ignore|as unknown)"

# 3 有没有加静默兜底
git diff HEAD~1 | grep -E "^\+.*catch.*\{.*return (null|false|\[\]|\{\});?\s*\}"

# 4 改动的函数有没有调用方覆盖（改了一个没人调的东西 = 可能是白改）
#    对每个改动的导出，查引用数
```

再加两条人工判断：

- **改动的函数，测试有没有跟着动？** 改了行为但测试没变 → 要么测试是假的，要么行为没真改
- **新增的文件，有没有被任何地方引用？** 孤立文件 = 半成品

---

## 红队的局限（必须说清）

> **红队独立，但它同样不知道"正确行为是什么"。**

它能查**形式**（有没有偷工减料、有没有放宽类型、有没有删断言），
不能查**语义**（这样算对不对、这个折扣该不该是 8 折）。

**语义只能靠人。** 别把红队当成最终把关。

---

## 什么时候值得开红队

| 场景 | 值得吗 |
|---|---|
| 单文件小改 | 不值得，成本高于收益 |
| 跨模块结构改动 | 值得 |
| 动核心计算 / 数据转换 | 强烈建议 |
| 一次超过 5 个文件 | 必须 |
| 改完自己觉得"挺顺的" | **特别值得**——越是顺畅越可能漏 |

---

## 怎么给红队下指令

```
你是审查方。只做一件事：判断这次改动有没有偷工减料。

你会拿到：git diff 范围、仓库路径。不会拿到作者的解释。
不许问作者为什么这么改。

按这个顺序做：
1. 跑 diff 纯度四条检查（删断言 / 放宽类型 / 静默兜底 / 孤立文件）
2. 对每个被改的函数，查它有没有调用方、调用方有没有测试
3. 报三类结果：
   - 确定的问题（附命令输出）
   - 可疑但无法确认（说明缺什么证据）
   - 检查过没问题的（说明查了什么）

不要给建议，不要重写代码。
```
