# slop-surgery

扫描并修复 AI 反复修改后遗留的代码问题，同时约束后续开发。

提供两种工作模式。一种处理已经混乱的代码，一种在既有代码上安全地增加功能。两种模式都要求在动手之前给出完整计划与验证方式，并且每次只处理一个可独立回滚的改动。

零依赖，语言无关。示例基于 TypeScript。

---

## 方法论来源

核心方法来自一次真实执行。目标项目包含 110 个源文件，Electron 与 React 技术栈，没有测试。完整审查后得到 8 条发现，其中 2 条来自项目自带的 lint，1 条来自 `git grep`，5 条来自逐行阅读代码。skill 中预设的症状扫描命令没有产生任何发现。

这次执行改变了整体设计。扫描能够给出规模与候选位置，无法定位实际问题。真正有效的手段是把两个本应一致的信息源放在一起比对。文档声称使用 zod 做校验，`package.json` 中不存在该依赖。lint 报告某组件的 return 语句位于多个 hook 之前，追查调用方后发现空数组已被过滤。两个名称相近的函数，函数体逐字相同。

8 条发现中有 7 条来自这类比对。因此主方法是寻找不一致，扫描命令只用于排除明显无关的区域。

## 工作流程

```
环境探测 → 扫描 → 诊断 → 输出报告与计划 → 等待授权 → 执行单片改动 → 验证 → 返回计划
```

第一步是环境探测。git 是否可用决定能否回滚。测试是否可运行决定能否验证等价性。build 与 typecheck 是否可用决定分析深度。源文件数量决定是否需要分区，超过 150 个进入分区模式，超过 800 个先做骨架蒸馏。缺失的能力需要在报告首行声明。

两种模式共用上述流程，差异在于改动方式。

surgery 模式处理已经混乱的代码，提供六种动作，依次为删除、合并、压平、拆分、迁移、重命名。默认按此顺序执行。删除先缩小改动面。合并让真实重复暴露。压平为后续拆分腾出空间。拆分放在靠后位置，过早拆分会把集中的复杂度分散到大量小文件中。迁移完成后结构才稳定。重命名最后执行，因为它需要对最终结构负责。

允许插队的情况有三种。存在会立即触发的缺陷。当前代码无法验证，需要先开测试口子。命名阻碍理解。插队需要在计划书中说明理由。

grow 模式处理在既有代码上增加功能的情况，提供两种战术。

Sprout 将新功能完整实现在新文件中，测试同样写在新增文件内，原有文件只增加一处调用，不展开新业务逻辑。

Wrap 将原函数重命名为 `xxxLegacyInternal`，新建同名函数包裹在外层，依次执行前置校验、调用原实现、后置审计，对外签名与返回值保持不变。

Wrap 会改变调用栈深度与函数身份。如果原函数被反射、装饰器、序列化或 `Function.name` 依赖，应改用 Sprout。执行前需要在仓库中检索原函数名与 `name`、`bind`、`caller` 的使用情况。

grow 模式的主要风险是演变为附带重构。增加功能过程中发现的问题记录到 `FINDINGS.md`，留待后续处理。

## 硬性规则

### 第一轮只输出计划

在收到明确授权之前，不修改任何文件，包括 Markdown、JSON、注释与格式。不执行会改变状态的命令。不创建或删除目录。不提交。

这条规则在一次越界之后加入。早期版本没有强制要求，第一次真实执行时修改了 11 个文件，没有产生任何提交，全部留在工作区。

授权的判定标准需要明确。以下表述视为授权，可以、开始、动手、改吧、执行。以下表述不视为授权，你看着办、随便、你觉得该改就改、我只是想看看、帮我分析一下、别太保守。提供目标路径不构成授权。

单片授权不等于整体授权。每一片完成后需要重新确认。

### 单片改动的边界

一片改动需要能够独立验证、独立回滚。上限为 5 个文件或 300 行，超出需要拆分。

每片完成后立即提交，信息以 `[surgery]` 或 `[behavior]` 开头。前者表示仅调整结构，后者表示改变行为并附验收方式，两类不允许混合在同一个提交中。

缺少提交意味着缺少可回退的切片历史，回滚只能整体 `restore`，单片回退的能力随之丧失。

### 验证标准前置

无法说明如何判断改动出错时，不允许执行改动。

没有测试的项目使用等价性验证，成本由低到高为三种方式。将原实现复制到临时文件，使用相同输入比较输出。保留临时导出，分别运行新旧实现比较结果。选取空值、单值、最大值、边界值各一到两个手工比对。

三种方式均不可行时，这一片不修改代码，改为在两处各添加一行同步说明注释。

## 核心方法

七个方法都在上述项目中产生过真实发现。

| | 比对对象 | 典型发现 |
|---|---|---|
| F1 | lint 报告 ↔ 源代码 | lint 报告某组件的 return 位于 7 个 hook 之前，阅读源码发现是 goal 为空时提前返回，追查调用方后确认空数组已被过滤，严重度从立即触发降为条件触发 |
| F2 | 同一事实的多个副本 | 版本号在 `build.gradle` 中为 0.1.59，`AGENTS.md` 写 0.1.8，README 写 0.1.31，backlog 写 0.1.37 |
| F3 | 文档 ↔ 代码事实 | `findings.md` 声称使用 zod 校验，`git grep -E "z\.object|safeParse"` 返回空，实际校验由 `schema.ts` 手写实现 |
| F4 | 名称相近的函数 | 两个 `toMinutes` 函数体逐字相同 |
| F5 | 同一文件内相邻的函数 | 名称不同但语义相同的实现只能通过顺序阅读发现 |
| F6 | 调用方 ↔ 被调用方 | 决定一条问题是立即触发还是条件触发 |
| F7 | 项目自有记录 ↔ 代码 | `backlog.md` 记录自写 WheelPad 后未删除 `react-wheel-picker`，该依赖已无引用 |

F2、F3、F7 成本最低，建议优先执行。

另有七种同类方法，包括字面量比对、环境变量比对、入口比对、测试名与断言比对、类型与运行时比对、双环境比对、跨层形状比对。逻辑成立但没有真实命中记录，使用时标注为推测性检查。

结论需要写明比对对象。仅陈述某处存在重复不构成发现，需要给出具体位置与比对过程。

## 常见问题形态

扫描前需要过一遍这张表，发现才能归类。完整版本在 `references/slop-patterns.md`，每条包含成因与误判边界。

| | 形态 | 特征 | 处理方式 |
|---|---|---|---|
| P1 | 并行双胞胎 | 两个函数体逐字相同，名称存在细微差异 | 合并 |
| P2 | 补丁摞补丁 | 5 至 8 层嵌套条件，每层附带一句判断说明 | 压平 |
| P3 | 过早抽象 | 一个接口配一个实现加一个工厂，改动一处需要触及 4 个文件 | 删除 |
| P4 | 幻觉依赖 | 已安装但零引用，或 `npm view` 无法查询 | 删除 |
| P5 | 吞错误 | `catch { return [] }`，失败后调用方无从得知 | 抛出、记录日志或声明降级 |
| P6 | 假测试 | 测试名承诺错误路径，断言中缺少 `toThrow` | 补充断言或删除 |
| P7 | 文档与代码分叉 | 文档提到的依赖未安装、命令不存在 | 修改文档 |
| P8 | 状态蔓延 | 派生数据被另存，effect 修改其他 store | 收敛为单向数据流 |
| P9 | 巨型文件 | 单文件 2000 行，承担七种职责 | 按意图拆分 |
| P10 | 类型逃生 | `any` 密度排在前列，或出现连续的 `as unknown as` | 修正数据形状 |

无法归类的条目可能属于业务复杂度，需要回到健康判定一节重新评估。

同一形态出现三次以上，说明流程层面存在问题。逐个修复会让它在其他位置重新产生，需要先补充约束再处理。

## 输出

第一轮输出包含报告、计划书与一句授权请求。

报告结构如下。

```
0. 环境与边界   基线 commit · 测试可用性 · 降级说明 · 局势评估
1. 规模与扫描   源文件数 · 全量或分区 · 骨架蒸馏
2. 发现         位置 · 问题描述 · 依据 · 严重度 · 处置结论
3. 整体结论     四种处置各自数量 · 健康判定结果
4. 建议顺序     第 1 片至第 N 片，仅写目标
5. 计划书       逐片，一页一张
6. 暂不处理项   每条三行，不修改原因、修改后的影响、解锁条件
7. 覆盖声明     已读取、未读取、已运行、未运行
8. 不确定项
```

第 6 节与第 7 节最容易被简化，也最能反映审查质量。未发现问题的结论必须附带范围说明。

计划书每片一张。

```
【第 N 片 / 共 M 片】
改哪        <文件与行号>（约 X 行）
为什么改    <一句话，附依据>
怎么改      <删除 / 合并 / 压平 / 拆分 / 迁移 / 重命名 / Sprout / Wrap>
连带        <需要同步修改的调用方，最多 5 个>
不做什么    <本片明确不触及的范围>
改坏判据    <执行什么、观察什么>
回退方式    <命令；是否支持单独回滚>
预计影响    <文件数、是否涉及数据或接口变更>
```

“不做什么”这一项用于限制改动范围。缺省时，改动过程中容易扩大到相邻代码。

## 约束文件

修复代码不足以阻止问题重新产生。下一轮 AI 进入项目时会沿用同样的写法。

`references/templates.md` 提供七个文件的模板。

| 文件 | 职责 | 上限 |
|---|---|---|
| `AGENTS.md`（根目录） | 硬性规则与索引 | 200 行 / 2000 token |
| `<模块>/AGENTS.md` | 职责、非职责、依赖边界 | 8 至 15 行 |
| `CONTEXT.md` | 术语表，一个概念对应一个名称 | 随项目增长 |
| `docs/adr/NNNN-*.md` | 设计决策与理由 | 一页一个 |
| `docs/FINDINGS.md` | 已知问题与未修复原因 | 随项目增长 |
| `docs/PLAN-<日期>.md` | 本轮改动清单、顺序与回退 | 一轮一份 |
| `TASK.md` | 单次任务的约定 | 半页 |

一条原则需要单独说明。能够由工具强制执行的规则不写入文档。文档只承载工具无法覆盖的内容，包括边界、职责、禁止事项与理由。

规则应使用禁止句式，例如“不许在未跑通既有测试的情况下修改核心计算逻辑”。建议句式会让 AI 跳过规则自行推测。

可选提供两个 git hook。`commit-msg` 强制提交标签，`pre-commit` 限制 300 行上限与 diff 纯度。安装 hook 会改变仓库行为，执行前需要确认。

## 不处理的范围

全仓治理看板、自动创建 PR、代码格式统一、完整安全审计、性能调优。

将“不熟悉该领域”判断为代码问题同样属于不处理范围。

豁免条件包括单文件不足 30 行、纯样式文案配置、既有模式内的小幅改动，以及明确要求直接编写的情况。满足任一条件时不启动流程。

## 验证状态

已在一个项目上完成验证。110 个源文件，111 次提交，零测试。产出 8 条发现、11 个文件改动与一份完整报告。该次执行暴露了 4 个设计缺陷，均已修正。其中影响最大的一项是早期版本未强制要求动手前等待授权，导致 AI 直接修改了 11 个文件。

以下部分尚未验证。

grow 模式未经过实际执行。它在真实使用中是否会演变为附带重构，目前只有文字约束，没有实测数据。

逆风场景未经过验证。上述项目的 `tsc` 零错误、lint 可用、模块职责清晰、项目自带 findings 与 backlog 文件。在缺少 tsc、缺少 lint、文件交叉引用严重、测试不可信的项目上，该流程是否成立尚不确定。

意图确认清单的实际填写率未知。该设计依赖使用者逐条确认隐含规则，填表本身存在摩擦。

diff 纯度审计的正则误报率未统计。`^\+.*\bany\b` 会匹配注释中出现的 “any” 一词。

上述顺利执行的结果不能作为 skill 有效性的证明。该结论同样写入 skill 末节。

## 安装与结构

```bash
git clone https://github.com/Colin-Fumina/slop-surgery.git
cp -r slop-surgery ~/.agents/skills/
```

仓库根目录即为 skill 根目录，克隆后可直接复制到 skills 目录使用。

```
slop-surgery/
├── SKILL.md                      主文件，常驻加载，610 行
├── README.md
├── LICENSE
└── references/
    ├── finding-methods.md        发现方法 F1 至 F14，扫描前必读
    ├── slop-patterns.md          十种问题形态图鉴
    ├── commands.md               症状检索命令，用于排除
    ├── templates.md              约束文件模板与 hook 脚本
    └── roles.md                  红蓝双角色分工
```

主文件常驻，`references/` 按阶段加载。单次快扫约占 9 至 11K token。

触发方式为自然语言描述，例如“这项目代码很乱，帮我梳理一下”或“加一个导出功能，不要破坏现有代码”。

## 参考

Google eng-practices 提供审查标准，其目标是代码整体健康度持续提升，不要求达到完美。Michael Feathers 的 Sprout 与 Wrap 是 grow 模式的原型。Martin Fowler 的重构目录是问题分类的来源。Microsoft 关于 workspace instructions 的反模式文档说明了不应将 linter 已覆盖的内容写入文档。

关于 AI 生成代码的观察包括单次提交超过 500 行、依赖幻觉、仅覆盖正常路径的测试、过早抽象、上下文衰减导致的架构漂移，以及变异杀伤率约 40% 的测试。

未采纳的设计包括多层治理看板、强制只读门禁、15 字段计划书、规则数量上限与阶段性路线图。这些设计会让 skill 自身成为需要维护的对象。
